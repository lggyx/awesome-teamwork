## 1. 定位与原则

- **定位**：开源团队协作工具软件。`awesome-` 只是项目代号，不采用 awesome-list 文档形态。
- **方法**：问题驱动开发（Problem-Driven）。不预设产品形态，先收集真实痛点，
  用证据收敛出"解决哪个问题"，再设计、开发、运营。
- **受众**：开源公开运营。因此从基建起就按公开仓库标准要求自己：
  文档可读、来源可溯、License 明确、不把私域信息带进仓库。

## 3. 文件约束（继承自 shared-brain / lggyx-articles）

1. 中文交流、中文注释；提交信息中文，`<类型>: <简述>`；git 身份 `lggyx`；**push 需用户确认**。
2. 诚实性最高优先级：不编链接、不编数据、没验证不标已验证、做不到就说做不到。
3. 产品方向、优先级、Go/No-Go 类决策归用户；Agent 提供带推荐的有限选项。
4. 写代码后按 AGENTS.md 的质量基线执行（完整可运行、异常处理、测试 3 组真实跑）。

## 4. 当前阶段：问题收集（细则）

### 4.1 收集渠道

| 渠道 | 说明 | 证据要求 |
|---|---|---|
| 自有经验 | 用户本人与所在团队的亲历痛点 | `source: self`，写明背景场景 |
| 开源社区 | GitHub 上同类工具的 issues / discussions（吐槽与 feature request） | issue 真实链接 |
| 公开讨论区 | Reddit（r/projectmanagement 等）、Hacker News、V2EX、知乎等 | 帖子真实链接 |
| 竞品反馈 | 竞品的用户评价、公开 changelog 里反复修补的点 | 可追溯链接 |

纪律：每个渠道只用真实检索到的内容；检索不到就如实说"该渠道本轮无收获"，
不拿编造的"调研结果"凑数。

### 4.2 问题卡片格式

一卡一文件，放 `docs/problems/`，命名 `P-NNN-<短slug>.md`，编号全局唯一。
格式与字段定义见 `docs/templates/problem-card.md`。

### 4.3 归类与去重

- 预设问题域（收集时暂用，阶段 2 允许重组；部署与运维、流程适配为
  首轮收集后新增，集成生态、安全与隐私为第二轮新增）：
  **沟通对齐 / 任务管理 / 文档知识 / 会议 / 进度可见性 / 跨团队协作 /
  远程异步 / 工具切换成本 / 部署与运维 / 流程适配 / 集成生态 / 安全与隐私**
- 相似问题不删卡，标 `status: merged` 并在卡内指向保留卡，保留原始证据。

### 4.4 阶段验收标准

- [ ] 问题卡片 ≥ 30 张，每张都符合模板字段
- [ ] 覆盖 ≥ 5 个问题域，每个域 ≥ 3 张
- [ ] `source: community/competitor` 的卡片 100% 带可访问的真实链接
- [ ] `source: self` 卡片由用户本人确认过（Agent 不代写"亲历"）
- [ ] 用户对问题地图做一次过目确认

## 5. 阶段 2~5 概要（先立框架，进入时再细化）

- **收敛定位**：按 痛感 × 频率 × 现有方案不足 三轴排序；输出定位文档（选哪个问题、
  给谁用、凭什么赢）与竞品矩阵；Go/No-Go 由用户拍板。
- **方案设计**：技术选型给有限选项带推荐；License 建议从 MIT / Apache-2.0 二选一，
  由用户决定；原型只验证核心假设。
- **MVP 开发**：按 AGENTS.md 质量基线；每个行为变更先有测试；CI 从第一天就上。
- **公开运营**：README 定稿、CONTRIBUTING、issue 模板、发布渠道（Show HN / V2EX /
  即刻等）；对外发布类操作逐次经用户确认。
